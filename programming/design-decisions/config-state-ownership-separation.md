# Configuration/state ownership separation

User-authored **configuration** and program-authored **state** must live in
different locations, have different owners, and follow different write paths. A
program must never mutate declarative configuration as a side effect of running.

This is the single rule that dissolves a whole class of tooling failures: config
files silently rewritten, comments and ordering lost, version-controlled files
going dirty on every run, and read-only managed config (Home Manager, Ansible,
a `/nix/store` symlink) getting clobbered.

## The rule: one writer per file

Every persisted file has exactly one authority that writes it.

- **Humans and configuration managers** write configuration.
- **Applications** write state, cache, and runtime data.

Two-way sync between a declarative config file and program-written state is a
recognized anti-pattern, not a missing feature. It cannot be made lossless —
comments, key ordering, and conflict semantics all break — so mature ecosystems
do not ship it. They dissolve the tension architecturally instead: the file was
never meant to have two writers.

> Corollary — **prefer read-only config.** If a program only ever reads its
> configuration, the file can be a symlink into an immutable store, generated by
> a config manager, or checked into git, and nothing the program does will ever
> make it drift.

## Be XDG-friendly first

The baseline requirement for any application we build or adopt: **follow the XDG
Base Directory Specification.** It already encodes this separation. Respect the
environment variables (with the documented fallbacks) and put each kind of file
where it belongs.

| Kind        | Owner               | App may write?  | XDG base (default)                   | Examples                                    |
| ----------- | ------------------- | --------------- | ------------------------------------ | ------------------------------------------- |
| **Config**  | user / config mgr   | no              | `$XDG_CONFIG_HOME` (`~/.config`)     | preferences, declared manifests, recipients |
| **State**   | application         | yes             | `$XDG_STATE_HOME` (`~/.local/state`) | project registry, last-used context, logs   |
| **Data**    | application         | yes             | `$XDG_DATA_HOME` (`~/.local/share`)  | generated assets the user keeps/backs up    |
| **Cache**   | application         | yes, disposable | `$XDG_CACHE_HOME` (`~/.cache`)       | derived/merged files, downloads             |
| **Runtime** | application/session | yes, ephemeral  | `$XDG_RUNTIME_DIR`                   | sockets, locks, pid files                   |

The Filesystem Hierarchy Standard draws the same line one level up: `/etc` is
static host configuration, `/var` is variable data written during operation, and
`/run` is runtime data. Twelve-Factor's _Config_ factor is the adjacent rule for
deployed services: config that varies between deploys is externalized from code.

## Who owns this file?

When you are unsure where something goes, answer one question — _who writes it?_

- The **user hand-edits** it → **config** (`$XDG_CONFIG_HOME`); read-only at
  runtime.
- The **program writes** it and the user never touches it → **state**
  (`$XDG_STATE_HOME`).
- The **program writes** it but the user needs a durable, portable copy →
  **data** (`$XDG_DATA_HOME`).
- It can be **regenerated** at any time → **cache** (`$XDG_CACHE_HOME`).
- It only lives for the session (sockets, locks) → **runtime**
  (`$XDG_RUNTIME_DIR`).

A runtime-generated registry (e.g. "projects this tool has seen") is **state by
definition** — it belongs in `$XDG_STATE_HOME`, never appended into a config file
under `$XDG_CONFIG_HOME`.

## Pattern A — config/state split with read-time merge

When a tool needs both declared intent _and_ runtime-accumulated entries, give
each its own file and merge them when reading — never write back into config.

```text
~/.config/<tool>/config.yaml        # DECLARED: user-authored, read-only, git/Nix-managed
~/.local/state/<tool>/registry.yaml # RUNTIME: tool-written, machine-local, disposable-ish
```

At startup the tool loads both and resolves precedence (declared ∪ runtime).
There is no sync step and no write-back, so the config file never drifts. This is
exactly how Kubernetes keeps _desired config_, _live state_, and the
`last-applied-configuration` annotation as three separate inputs for its
three-way merge, and how Helm 3 reconciles old manifest + live state + new
manifest without treating any one of them as a mutable blob.

## Pattern B — drop-in directory

When multiple writers must contribute to one logical configuration, don't have
them rewrite a shared file — give each a **drop-in** and read the directory in
deterministic order (later files override earlier ones).

```text
~/.config/<tool>/config.d/10-base.yaml     # read-only base (vendor / config manager)
~/.config/<tool>/config.d/90-local.yaml    # writer B's slice
```

We **enable this standard mechanism** wherever a tool needs local extensibility.
It is the proven model behind systemd (`*.conf.d/`, unit drop-ins),
`sshd_config.d`, `sudoers.d`, `logrotate.d`, and git's `include` / `includeIf`.
A vendor or config manager owns a read-only base; a second owner adds entries in
its own file. No rewrites, no conflicts, no bidirectional sync.

## Anti-patterns

- **Appending runtime state to a user-authored config file.** The classic
  failure: registering entries into `~/.config/<tool>/*.yaml` on the fly.
- **Rewriting config to normalize, migrate, sort, or persist UI state.** A
  whole-file "read → transform → atomic `mv`" strips comments and reorders keys,
  and clobbers a managed symlink.
- **Two-way sync** between declarative config and generated state — it can't be
  lossless; don't build it.
- **Treating read-only config as an error** for a command that only needs to
  write _state_. If `login` needs to persist a token, that token is state.

## Precedents and case studies

- **XDG Base Directory Specification** — the direct authority for the
  config/state/cache/runtime split.
- **Filesystem Hierarchy Standard (FHS)** — `/etc` vs `/var` vs `/run`, the same
  split at system level.
- **Twelve-Factor App, _Config_** — externalize deploy-varying config from code
  (adjacent, narrower).
- **systemd drop-ins** and **`sshd_config.d` / `sudoers.d`** — the canonical
  layered-composition precedent (Pattern B).
- **Kubernetes server-side apply / three-way merge** and **Helm 3** — desired
  config, live state, and last-applied kept as separate inputs (Pattern A).
- **Real incidents** where tools got it wrong and the fix was to _move state
  out of config_: the GitHub CLI requiring a writable `config.yml` (breaks
  immutable / Home-Manager-managed config), lazygit moving `state.yml` into
  `$XDG_STATE_HOME` (#2794), and k9s no longer writing runtime context into
  `config.yaml` (#2346).

### Worked example: `dctl`

`dctl` originally treated `~/.config/dctl/projects.yaml` as both configuration
(the user declares projects/manifests) _and_ state (`dctl init` registers
projects at runtime, via a whole-file rewrite). Under Home Manager that file is a
read-only `/nix/store` symlink, so the runtime rewrite clobbers it — the failure
this article exists to prevent.

The fix is not in the config manager; it is in the tool. Split
`~/.config/dctl/projects.yaml` (declared, read-only) from
`~/.local/state/dctl/registry.yaml` (runtime, writable) and merge on read
(Pattern A). The config manager's wiring then collapses to a plain read-only
symlink — no out-of-store gymnastics, no activation merge, no drift.

## Author checklist

Before shipping a tool that persists anything, walk this:

1. **Does it read user-authored configuration?** → Put it under
   `$XDG_CONFIG_HOME` and treat it as **read-only**.
2. **Does it ever write that config file?** → Stop. Either make it read-only, or
   move the written fields to state and merge on read (Pattern A).
3. **Does it accumulate runtime entries / last-used values?** → `$XDG_STATE_HOME`.
4. **Is the output regenerable?** → `$XDG_CACHE_HOME`. **Ephemeral/session?** →
   `$XDG_RUNTIME_DIR`.
5. **Do multiple owners contribute to one config?** → Use a drop-in `*.d/`
   directory (Pattern B), not a shared rewritten file.
6. **Document it:** state plainly "the user edits X; the tool manages Y."
