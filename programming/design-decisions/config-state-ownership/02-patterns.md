# Patterns

Two proven shapes for tools that need both declared intent and runtime-written
data, plus the reason read-only config is the goal.

## Pattern A — config/state split with read-time merge

When a tool needs both declared intent _and_ runtime-accumulated entries, give
each its own file and merge them when reading — never write back into config.

```text
~/.config/<tool>/config.yaml        # DECLARED: user-authored, read-only, git/Nix-managed
~/.local/state/<tool>/registry.yaml # RUNTIME: tool-written, machine-local, disposable-ish
```

At startup the tool loads both and resolves precedence (declared ∪ runtime).
There is no sync step and no write-back, so the config file never drifts. This is
exactly how Kubernetes keeps _desired config_, _live state_, and the
`last-applied-configuration` annotation as three separate inputs for its
three-way merge, and how Helm 3 reconciles old manifest + live state + new
manifest without treating any one of them as a mutable blob.

## Pattern B — drop-in directory

When multiple writers must contribute to one logical configuration, don't have
them rewrite a shared file — give each a **drop-in** and read the directory in
deterministic order (later files override earlier ones).

```text
~/.config/<tool>/config.d/10-base.yaml     # read-only base (vendor / config manager)
~/.config/<tool>/config.d/90-local.yaml    # writer B's slice
```

We **enable this standard mechanism** wherever a tool needs local extensibility.
It is the proven model behind systemd (`*.conf.d/`, unit drop-ins),
`sshd_config.d`, `sudoers.d`, `logrotate.d`, and git's `include` / `includeIf`.
A vendor or config manager owns a read-only base; a second owner adds entries in
its own file. No rewrites, no conflicts, no bidirectional sync.

## Prefer read-only config

Both patterns exist to reach one end state: **a program that only ever reads its
configuration.** When that holds, the config file can be a symlink into an
immutable store, generated by a config manager, or checked into git, and nothing
the program does will make it drift.

### Why runtime config-mutation breaks under Nix / Home Manager

The failure this whole topic exists to prevent is concrete. Home Manager renders
a program's config into the **immutable `/nix/store`** and symlinks it into place:

```text
$ ls -l ~/.config/<app>/config.toml
lrwxrwxrwx  ~/.config/<app>/config.toml -> /nix/store/<hash>-<app>-config/config.toml
```

The store path is world-readable and **read-only**. If the program tries to write
to `~/.config/<app>/config.toml` at runtime — even to stash a "last used" field —
the write either fails outright (read-only target) or is silently discarded on
the next `home-manager switch`, which re-materializes the file from the store.

The principle in one line: **declarative config is an _input_, not an _output_.**
Reproducibility requires that the same config file always yields the same
behavior, which is impossible if the program writes back into it. The same
reasoning applies to Ansible, Salt, or a plain dotfiles repo: any owner that
_generates_ the config expects it to stay as written.

The fix is never in the config manager; it is in the tool. Keep config read-only
and route every runtime write to state, cache, or runtime per
[01 — Placement](./01-placement-xdg-fhs.md#who-owns-this-file). See
[03 — Anti-patterns & case studies](./03-anti-patterns-and-case-studies.md) for
the incidents where tools got this wrong and the `dctl` worked example.
