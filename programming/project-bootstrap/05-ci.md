# 05 — CI

Stand up continuous integration, so every change is built, tested, and gated before it lands.

## First CI workflow

Add a CI workflow that, on every push and pull request, enters the devshell of the Nix flake from
chapter [03](./03-local-dev-environment.md) and repeats the two hook stages of chapter
[04](./04-quality-gates.md#git-hooks):

```bash
nix develop --command pre-commit run --all-files
nix develop --command pre-commit run --all-files --hook-stage pre-push
```

CI holds no check of its own and installs no project tool outside the devshell, so a push that
passed its hooks passes CI. The job names it emits are what any required-status-check configuration
will name, so name them deliberately.

## CI-only checks

A push-started check runs only in CI when it cannot run locally: it needs a secret, a second
operating system, or a service that only the forge offers. A long runtime is no such reason, because
a costly check runs at pre-push. The project lists each exception and its reason in its contributor
guide, and the list is empty when there is none.

The same list names two kinds of job that are not CI-only checks, so that it names every CI job:

- A report-only job, such as CodeQL or Scorecard, uploads findings and never fails on one. It is not
  a check, and the list names it as report-only.
- A scheduled job that no push starts, such as a nightly mutation test or benchmark, is outside the
  rule, and the list names it as scheduled.

`bootstrap-ci` scaffolds the CI workflow (GitHub Actions / GitLab CI), reusing the project flake.
