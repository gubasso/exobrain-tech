# 05 — CI

Stand up continuous integration, so every change is built, tested, and gated before it lands.

## First CI workflow

Add a CI workflow that, on every push and pull request, enters the devshell of the Nix flake from chapter [03](./03-local-dev-environment.md) and repeats the hook stages of chapter [04](./04-quality-gates.md#git-hooks). Each step names its stage and its group filter, as [04 — Hook scopes](./04-quality-gates.md#hook-scopes) shows in a worked example:

```bash
nix develop --command prek run --all-files --stage pre-commit --no-group local-only
nix develop --command prek run --all-files --stage pre-push --no-group local-only
nix develop --command prek run --all-files --stage manual --group ci-only
```

A project with no `ci-only` hook leaves the third step out, because prek refuses a `--group` that matches no hook.

CI holds no check of its own and installs no project tool outside the devshell, so a push that passed its hooks passes CI. The job names it emits are what any required-status-check configuration will name, so name them deliberately.

A CI runner is a host, so the workflow supplies the host tools that the project needs, as a developer machine does: Nix and prek for every project, and uv for a uv project. The devshell holds no hook runner, and the devshell of a uv project holds no uv and no Python. `nix develop` keeps the `PATH` of the runner, so `prek run` and `uv run` work inside it. On GitHub Actions, `j178/prek-action` with `install-only: true` installs prek without running it ([prek CI](https://prek.j178.dev/ci/)). On GitHub Actions, `astral-sh/setup-uv` installs the newest uv that `[tool.uv] required-version` in `pyproject.toml` accepts when the step names no version, and its `cache-python` input keeps the managed CPython between runs ([setup-uv](https://github.com/astral-sh/setup-uv), v10.3.3, read 2026-11-11):

```yaml
- uses: actions/checkout@<sha> # fetch-depth: 0 where a hook scans the history
- uses: astral-sh/setup-uv@<sha>
  with:
    enable-cache: true
    cache-python: true
- uses: j178/prek-action@<sha>
  with:
    install-only: true
- uses: cachix/install-nix-action@<sha>
- run: nix develop --command prek run --all-files --stage pre-commit --no-group local-only
- run: nix develop --command prek run --all-files --stage pre-push --no-group local-only
```

A project that follows the canon of exobrain-tech runs the hook `hook-revisions`, which calls the `exobrain` CLI, and can run `exobrain host-check` in a recipe. The devshell holds no `exobrain` ([03 — Host requirements](./03-local-dev-environment.md#host-requirements)), so each job that calls it installs the CLI of the release that the project pins. The step reads the tag from the exobrain-tech entry of `.pre-commit-config.yaml`, so the pin has one owner. It downloads the release archive and checks its GitHub artifact attestation, which the release workflow of exobrain-tech signs. It runs before the first step that calls `exobrain`. On GitHub Actions, `yq` and `gh` come with the runner:

```yaml
- name: Install the exobrain CLI of the pinned exobrain-tech tag
  env:
    GH_TOKEN: ${{ github.token }}
  run: |
    tag=$(yq '.repos[] | select(.repo | test("/exobrain-tech(\.git)?/?$")) | .rev' .pre-commit-config.yaml)
    asset=exobrain-x86_64-unknown-linux-gnu.tar.xz
    gh release download "$tag" --repo gubasso/exobrain-tech --pattern "$asset" --dir "$RUNNER_TEMP"
    gh attestation verify "$RUNNER_TEMP/$asset" --repo gubasso/exobrain-tech
    mkdir -p "$RUNNER_TEMP/exobrain"
    tar -xJf "$RUNNER_TEMP/$asset" -C "$RUNNER_TEMP/exobrain" --strip-components=1
    echo "$RUNNER_TEMP/exobrain" >> "$GITHUB_PATH"
```

GitHub Actions sets `GITHUB_ACTIONS`, and some tools force colored output there, such as Typer for its help text. A test that reads the output of such a tool strips the color codes, and runs once with the variable set, so the hooks see what CI sees.

## CI-only checks

A push-started check runs only in CI when it cannot run locally: it needs a secret, a second operating system, or a service that only the forge offers. A long runtime is no such reason, because a costly check runs at pre-push. The hook configuration declares each exception with its group, as [04 — Hook scopes](./04-quality-gates.md#hook-scopes) says: `ci-only` for a hook that only CI runs, and `local-only` for a hook that CI cannot run. The comment above the hook states the reason, and the contributor guide repeats each reason in one line.

The contributor guide also names two kinds of job that no hook declares, so that it names every CI job:

- A report-only job, such as CodeQL or Scorecard, uploads findings and never fails on one. It is not a check, and the guide names it as report-only.
- A scheduled job that no push starts, such as a nightly mutation test or benchmark, is outside the rule, and the guide names it as scheduled.
