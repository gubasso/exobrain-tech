# 00 — Overview

A flake pins the toolchain (language runtimes + system tools) and gives every checkout a
reproducible dev shell. [direnv](https://github.com/nix-community/nix-direnv) enters that shell
automatically on `cd`. Dependency resolution stays with the language's own package manager (uv,
npm, cargo, …).

- [Nix flakes](https://nix.dev/concepts/flakes.html)
- [nix.dev — declarative shell](https://nix.dev/tutorials/first-steps/declarative-shell.html)
- [nix-community/nix-direnv](https://github.com/nix-community/nix-direnv)

## The three files (per project)

Every Nix-managed project commits exactly three files:

- **`flake.nix`** — declares `devShells.default` (the toolchain). Committed.
- **`flake.lock`** — pins every input to an exact revision. Committed; generated by `nix`, **never**
  hand-written, and excluded from the hooks that rewrite or judge
  ([generated files](../../programming/project-bootstrap/04-quality-gates.md#generated-files)).
- **`.envrc`** — `use flake`, so direnv auto-enters the shell on `cd`. For Python, `layout uv`
  follows it and syncs and activates the uv venv
  ([02-per-project-devshell](./02-per-project-devshell.md#python-and-uv-in-a-devshell)).

Also add `.direnv/` and `/result` to `.gitignore`.

Pinning inputs is one instance of a general rule — state the values a guarantee rests on instead of
inheriting them, so an upstream change cannot alter your behavior without a diff in your repo. See
[Pin the values a guarantee rests on](../../programming/design-decisions/pin-values-guarantees-rest-on.md).

## Mental model

```bash
cd ~/Projects/foo          # .envrc present + trusted
      │
      ▼  direnv hook fires
use flake  ─────────────►  nix builds/loads devShells.default  ─────►  toolchain on PATH
      │                     (cached by nix-direnv after first eval)
      ▼
cargo / uv / pnpm ...      # deps resolved by the language manager, inside the shell
```

Leave the shell (`cd ..`) and direnv reverses the PATH changes. Nothing is installed globally per
project; the toolchain lives in the Nix store and is garbage-collected only when no gcroot
references it (nix-direnv keeps one under `.direnv/`).

## Why not just `nix profile add` everything?

`nix profile` is an imperative global profile — good for **user CLIs** you always want; keep it
lean. Anything tied to a _specific_ project belongs in that project's flake devShell, not the global
profile: not just its language toolchain (so each repo pins its own node/python/rust version
reproducibly, independent of what's globally installed), but also its **task runner and the tools
no other owner declares** (`just`, `statix`, …). The git hook runner, prek, is a host tool beside
git, because git runs a hook from every shell. Rule of thumb: if only
some projects need it — or it wants a project-pinned version — it goes in the project, not the
profile. The manifest and `.pre-commit-config.yaml` own what they can declare
([Who owns each dependency](../../programming/project-bootstrap/03-local-dev-environment.md#who-owns-each-dependency)).
